# Paseo role-workflow 대응 규칙

> 에이전트 규칙 세트 v1.0 · 2026-10-31 · 일반개발(계약 3)·연합개발의 plan·execute 대화가 읽는다.
>
> 이 문서는 규칙 세트(00–30)를 Paseo 플러그인 role-workflow의 역할·상태 블록·안전장치·푸시에 대응시킨다. **플러그인의 실제 동작·필드·기본값의 원본은 플러그인 코드다**(플러그인 저장소). 이 문서의 수치와 파일명은 2026-10-31 기준 설명이며, 코드와 다르면 코드가 현재 동작이고 이 문서를 고친다.

## 1. 역할 대응

role-workflow는 최초 기획·설계·검증 대화와 선택한 별도 구현 대화를 짝지어 두고, 각 응답 끝의 상태 블록을 읽어 다음 메시지를 상대 대화에 넘긴다.

| role-workflow 역할 | 기본 담당 | 맡는 규칙 문서                | 하는 일                                                                                                  |
| ------------------ | --------- | ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| 계획(plan)         | 최초 모델 | 10-planning + 30-verification | 조사, 원인 분석, 계획·설계, 수락 시험, 인계, 결과 검토와 판정, 현재 명세 반영. 제품 코드는 고치지 않는다 |
| 실행(execute)      | 선택 모델 | 20-implementation             | 인계대로 구현, 자체 검증, 결과 보고                                                                      |

- plan 대화의 유일한 실행 예외는 **사용자가 명시적으로 승인한 푸시**다(4절). 그 외에 제품 코드·설정·스키마를 바꾸지 않는다.
- plan과 execute가 같은 모델이면 단일 모델 모드다(공통 3.3). 판정 보고에 "단일 모델 검증"을 적고, 고위험은 다른 모델 검증 전까지 최대 부분 완료다.
- 대화별 시스템 지침은 플러그인이 `사용자 규칙 → 규칙 안내 블록 → 진행 방식 질문 → 역할 블록 → 자동화 블록` 순으로 쌓는다. 원본은 플러그인 저장소 `rules/`. 실행 중에는 플러그인이 사용자 데이터 폴더에 사본을 비치하며, 경로는 대화의 규칙 안내 블록에 나온다. 규칙 본문과 프로젝트 지침 파일 본문을 프롬프트에 복사하지 않는다. 비치에 실패하면 오류를 기록하고 규칙 안내 블록만 생략한다.

## 2. 상태 블록과 인계 문서

상태 블록의 정확한 필드와 형식은 플러그인 계약(`shared/contracts.ts` 등)이 원본이다. 아래는 각 상태에 무엇을 담는지에 대한 규칙이다.

| 상태       | 내는 쪽     | 규칙상 의미                           | 담을 것                                                                                                                                                                                                                          |
| ---------- | ----------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `plan`     | plan        | 기획설계 인계(첫 지시) 또는 보완 지시 | `next`: `작업 ID:`로 시작. `handoff.md` 경로, 이번 지시의 범위, 위험도(공통 4절), 필요한 증거 수준(공통 5절 번호), 수락 시험 위치·상태. 보완 지시면 판정 보고(`verdict.md`) 경로, 차단 지적 번호, 미완료 원인 분류               |
| `result`   | execute     | 구현 인계 보고                        | `impl-report.md` 경로와 판단 상태(구현 완료 / 부분 구현 / 보류), 도달한 증거 수준, 실제 실행한 검증, 미검증 범위. 2절 멈춤 보고도 `result`로 내고 판단 상태를 "보류(2절 보고)"로 적는다                                          |
| `complete` | plan        | 검증 완료 판정                        | 30-verification 7.1 완료 조건을 모두 충족했고 `verdict.md`가 있으며, 현재 명세 반영(10-planning 2.1)을 끝냈거나 반영 작업을 tasks에 남겼을 때만 낸다. `verdict {path, judgement, condition}`에 보고 경로·판정·검증 조건을 적는다 |
| `continue` | 같은 역할   | 같은 역할이 이어서 작업               | 무엇을 이어서 하는지 한 줄                                                                                                                                                                                                       |
| `input`    | 어느 쪽이든 | 사용자 결정 대기                      | `[미확정]` 항목, 선택지와 영향, 권고. 사용자 승인이 필요한 범위·계약·안전·규제·고위험 변경, 역할 규칙 충돌, 독립 검토 주체가 없을 때                                                                                             |
| `note`     | 어느 쪽이든 | 답변만, 흐름 유지                     | 흐름을 바꾸지 않는 답변                                                                                                                                                                                                          |

- **계획 → 실행:** plan의 `next`에 인계서 전문을 붙이지 않는다. 원본은 `handoff.md`이고 `next`에는 경로와 이번 지시에 필요한 요약만 넣는다(공통 6.2).
- **실행 → 검토:** 플러그인의 검토 문구는 30-verification 3.2–7절에 따라 handoff·impl-report와 실제 변경 파일·시험을 직접 확인하도록 요구한다. plan 대화는 설계 적합성(4.2)을 따로 판정하고 작업 문서 폴더에 `verdict.md`를 쓴다. 완료 조건 충족 시 `complete`, 부분 완료·미완료면 원인을 분류해 구체적 수정 계획과 함께 `plan`을 반환한다.
- **보완 루프:** 부분 완료·미완료면 plan은 원인을 분류해(10-planning 7절) 새 `plan`을 낸다. 원인이 설계·시험 오류면 먼저 설계 문서·수락 시험을 고치고 그 경로를 `next`에 적는다. 원인이 요구 변경이면 `input`으로 사용자 승인을 먼저 받는다.
- **역할 위반:** 플러그인은 역할과 맞지 않는 상태(계획 담당의 `result`, 실행 담당의 `plan`)를 처리하지 않는다. 이것을 우회하려고 다른 상태로 같은 내용을 보내지 않는다.
- **완료 판정 확인:** 계약 3의 일반·연합개발은 계획 담당 `complete`에 완료 판정·접근 가능한 보고 경로가 필요하다. 없으면 상태 블록만 1회 다시 요청하며, 여전히 불일치면 사용자 확인 대기로 남긴다. 같은 모델의 별도 대화는 조건을 단일 모델로 기록한다. 계약 2의 이전 연합개발은 재요청 뒤 경고만 표시하는 이전 동작을 유지하고, 계약 1의 이전 일반개발에는 이 게이트를 소급 적용하지 않는다. 다른 상태의 판정은 저장만 한다.
- **상태 블록 누락:** 플러그인이 상태 블록만 다시 내라고 요청하면 본문을 다시 쓰지 않고 상태 블록만 낸다.

## 3. 안전장치와 규칙

| 안전장치(코드 기본값)                                                                                | 규칙상 대응                                                                                                                                                    |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 왕복 제한: 계획→실행→검토 기본 5회(`maxCycles`), 전체 응답 30회(`maxTurns`). 넘으면 사용자 확인 대기 | 제한 안에 끝내려고 수락 기준·시험을 완화하지 않는다(20-implementation 5.1). 한도에 다가가면 남은 차단 지적, 반복된 원인 분류, 권고를 정리해 `input`으로 올린다 |
| 역할 위반 차단                                                                                       | 2절. 역할 경계는 규칙에서도 동일하다                                                                                                                           |
| 상태 블록 누락 복구                                                                                  | 2절                                                                                                                                                            |
| 컨텍스트 압축: 사용량이 기준(기본 0.8)을 넘으면 같은 대화 안에서 압축하고 handoff 기록으로 이어 감   | 압축 뒤에는 공통 8절대로 규칙 문서와 작업 문서를 실제로 다시 읽는다. 플러그인의 handoff 기록은 이어 가기 위한 메모이며 승인·검증의 증거가 아니다               |
| 자동 재개: 사용량 한도·일시 오류로 멈추면 자동으로 이어서 진행                                       | 재개 직후 마지막 상태 블록과 작업 문서의 상태를 대조하고, 이미 실행한 변경·푸시를 반복하지 않는다                                                              |
| 같은 폴더 동시 수정 감지·경고                                                                        | 경고가 나면 해당 작업을 멈추고 보고한다(10-planning 7절 동시 수정). 다른 대화의 변경을 확인 없이 덮어쓰지 않는다                                               |

위 수치는 코드 기본값이다. 실제 저장된 설정은 사용자 데이터 폴더의 `role-workflow/state.json`에서 다를 수 있다(`PASEO_HOME` 미지정 시 `~/.paseo/role-workflow/state.json`). 개인별 실제 값은 이 공용 규칙에 기록하지 않는다. 규칙이 수치를 전제해야 할 때는 실제 설정을 읽기 전용으로 확인하고, 확인 날짜와 `[확인]` 또는 `[미확인]`을 작업 문서에 적는다.

## 4. 푸시

- 플러그인은 응답의 `pushTargets`와 `verification` 기록을 모아 푸시 승인 화면에 보여 준다. **`verification`에는 실제로 실행한 검증만** 적는다. 실행 명령·결과·증거 수준(공통 5절 번호)을 쓰고, 하지 않은 것은 `[미실행]`으로 적는다. 대역 통합을 실제 실행으로 적지 않는다.
- 푸시 승인 패널은 기록된 판정·검증 조건·보고 경로를 표시한다. 완료 판정이 없거나 완료가 아니면 확인 경고를 표시하지만 푸시 버튼 조건·사용자 승인·원격 반영 확인 동작은 바꾸지 않는다. 이전 작업에 판정이 없을 때도 경고만 표시한다.
- 푸시 대상(`pushTargets`)은 검증 역할이 완료로 판정한 작업에서만 제안한다. 부분 완료·미완료 작업은 사용자가 명시적으로 요청하지 않는 한 제안하지 않으며, 요청받아 제안할 때는 판정과 남은 조건을 함께 보인다.
- 푸시는 사용자가 명시적으로 승인한 뒤에만, 승인받은 대화가 직접 실행하고 원격 해시까지 확인한다. 완료 판정이나 다른 모델의 동의는 푸시 승인이 아니다.
- 작업 상태 표시(계획 보라 → 진행 주황 → 완료 초록 → 푸시 또는 푸시 불필요 파랑)의 "완료"는 검증 역할의 완료 판정과 같은 뜻으로 쓴다.

## 5. 진행 방식 선택

- 진행 방식 질문과 기본값은 호스트 설정을 따른다. 일반개발과 연합개발은 표시·선택을 유지하며, 계약 3부터 역할과 자동 왕복 엔진을 공유한다. 일반개발을 내부적으로 연합개발로 바꿔 처리하지 않는다.
- 일반개발의 역할·인계 원칙은 공통 3.4가 원본이다. 조사 전에 구현 에이전트를 단독 질문으로 고르고, 해당 제공자의 모델·추론을 한 번의 질문으로 함께 고른다. 카탈로그는 실행 중인 호스트에서 읽는다. 연합개발은 기존 실행 모델 선택 흐름을 사용한다.
- 최초 plan의 ID·모델·추론을 보존한다. 구현 선택을 저장한 뒤 설계 인계 시점에 같은 workspace에 execute 탭을 만들고 실행한다. 원문 목표만 넘겨 구현 모델이 기획부터 다시 시작하지 않는다.
- 구현 대화의 권한 모드는 선택한 제공자의 기존 실행 설정(`claudeExecutorMode` / `executorMode`)을 사용한다. 생성·전달 의도를 먼저 저장하고 동일한 ID·idempotencyKey·메시지 ID로 재시도한다.
- `askExecutorModel`과 `rememberProjectChoices` 설정을 유지한다. 예전 `general` 선호도는 구현 담당 추천값으로 사용하며 최초 모델을 바꾸지 않는다. 화면에는 두 담당과 현재 단계를 각각 표시한다.
- 기존 일반개발의 담당 교체·단일 대화 실행 경로는 이전 계약의 재시작·인계 복구에만 남긴다. 기존 대화·보관·푸시 기록은 읽기만으로 재배정하지 않는다.
- 어느 쪽이든 담당 모델·추론 강도는 인계 문서와 판정 보고의 검증 조건에 적는다.
