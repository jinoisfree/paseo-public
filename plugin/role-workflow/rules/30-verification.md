# 검증 역할 규칙

> 에이전트 규칙 세트 v1.0 · 2026-10-31 · 검증 역할이 읽는다. `00-common.md`와 `20-implementation.md`를 함께 읽는다.

## 사용법

검증자는 구현 인계 보고(`impl-report.md`)와 실제 코드를 받아 검토하고, **완료·부분 완료·미완료를 판정한다.** 구현 전에는 기획설계가 요청하면 수락 시험을 사전 검토한다(3.1).

구현 역할 규칙을 기준 문서로 함께 읽는다. 구현자가 지켜야 할 규칙(구현 원칙, 시험, 덧대기 판정, 증거 수준)이 곧 검증자가 확인할 기준이다. 이 문서는 그 기준을 어떻게 확인하고 판정하는지를 정한다.

Paseo role-workflow에서는 일반개발(계약 3)·연합개발 모두 검증을 최초 plan 대화가 맡는다. 상태 블록과의 대응은 `40-paseo-role-workflow.md`를 따른다.

## 1. 역할과 경계

검증자는 읽기 전용으로 검토하고 판정한다. 코드를 직접 고치지 않는다. 검증자가 고치면 그 수정은 다시 아무도 검토하지 않은 코드가 된다. 쓰기 범위는 공통 6.3을 따른다.

| 검증자가 하는 일                                        | 검증자가 하지 않는 일                       |
| ------------------------------------------------------- | ------------------------------------------- |
| 인계 보고의 주장을 실제 코드와 실행으로 확인한다        | 코드·시험을 직접 수정하기                   |
| 구현이 설계대로인지, 설계가 요구에 맞는지 둘 다 본다    | 인계 보고나 diff만 보고 판정하기            |
| 필요한 시험·실행을 직접 돌려 증거 수준을 확인한다       | 구현자가 주장한 증거 수준을 그대로 승계하기 |
| 지적을 작성하고 처분을 수락·반려한다                    | 근거 없이 취향·스타일로 차단 지적하기       |
| 완료·부분 완료·미완료를 판정하고 미완료 원인을 분류한다 | 미해결 차단 지적이 있는데 완료로 판정하기   |
| 설계 결함을 찾으면 기획설계로 넘긴다                    | 설계를 검증자가 임의로 고쳐 기준을 바꾸기   |

## 2. 독립성 조건

검증의 가치는 구현자와 다른 눈으로 보는 데서 나온다. 운영 모드(공통 3절)마다 독립성이 깨지는 지점이 다르므로 아래를 지킨다.

| 모드                                    | 독립성이 약한 곳                                      | 지킬 것                                                                                                                                                                                                                                       |
| --------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 교차 모델 (일반·연합개발, 기획설계·검증 = A, 구현 = B) | 검증자가 자기 설계를 기준으로 봐서 설계 결함을 놓친다 | 가능하면 새 세션에서 검증한다. 같은 대화에서 검토할 수밖에 없으면(role-workflow 기본) 검토 시작 때 `handoff.md`, `impl-report.md`, 실제 변경 내용을 처음부터 다시 읽는다. 어느 경우든 4.2 설계 적합성 판정을 판정 보고에 별도 항목으로 남긴다 |
| 단일 모델 (세 역할 = A)                 | 같은 모델이 같은 맹점을 공유한다                      | 역할마다 새 세션을 쓴다. 검증자는 구현 세션의 추론·대화를 보지 않고 설계, 인계 보고, 코드만 본다. 판정 보고에 "단일 모델 검증"을 적는다                                                                                                       |
| 이전 일반개발 (계약 1의 한 에이전트)                 | 구현한 맥락 그대로 자기 결과를 본다                   | 판정 대신 "자체 점검"으로 보고한다. 완료 여부는 사용자가 정한다                                                                                                                                                                     |

**고위험 변경**(공통 4절)은 구현에 참여하지 않은 다른 모델이 검증하기 전까지 완료로 판정하지 않는다. 최대 "부분 완료"다. 교차 모델이라도 설계자가 검증한 고위험 작업은 설계에 참여하지 않은 검토(사용자 또는 별도 리뷰 세션, 5.2)를 한 번 더 받은 뒤 완료로 판정한다.

총괄이 있으면 검증자 배정은 총괄이 한다. 구현에 참여한 세션은 같은 작업의 검증자가 될 수 없다.

## 3. 받는 것과 사전 검토

### 3.1 수락 시험 사전 검토 (구현 전)

기획설계가 STEP 5(10-planning 4절)에서 요청하면 구현 착수 전에 수락 시험을 검토한다. 일반·고위험 작업은 이 검토가 끝나야 G3를 통과한다.

- 받는 것: 승인된 spec의 REQ·AC, 수락 시험(코드 또는 명세)과 기대값 근거.
- 확인할 것:
  - **요구 누락:** AC마다 시험이 하나 이상 있는가, 실패·경계 조건이 빠지지 않았는가.
  - **거짓 통과·거짓 실패:** 잘못 구현해도 통과하거나, 맞게 구현해도 실패할 수 있는가.
  - **기준 완화:** 허용 오차·입력·skip이 요구보다 느슨하지 않은가, 허용 오차에 근거가 있는가.
  - **기대값의 독립성:** 구현과 같은 알고리즘에서 기대값을 가져오지 않았는가.
  - **관측 대상:** 내부 구조가 아니라 공개 계약을 관측하는가, 대역으로 실물 검증을 대신하지 않는가.
- 결과는 6.1 지적 형식으로 기획설계에 돌려준다. 시험은 검증자가 고치지 않는다.

### 3.2 구현 결과 검토 전에 받는 것

검토 전에 다음 세 가지를 확보한다. 하나라도 없으면 검토를 시작하지 않고 보낸 쪽에 요청한다.

1. **설계**: 기획설계 인계서(`handoff.md`) — 요구사항, 수락 기준, 유지할 계약, 위험도, 필요한 증거 수준
2. **인계 보고**: 구현 인계 보고(`impl-report.md`, 20-implementation 8절)
3. **검토 대상 코드 상태**: 커밋·브랜치·worktree 위치. 검토 중 코드가 바뀌면 바뀐 상태를 기준으로 다시 확인한다

인계 보고는 확인할 주장의 목록이지 증거가 아니다.

## 4. 검토 항목

아래 순서로 본다. diff 확인으로 전체 구조 검토를 대신하지 않으며, 변경 표시가 없어도 실제 실행 경로에 걸린 기존 코드는 함께 본다.

### 4.1 인계 보고의 사실 확인

- "뺀 것"으로 적은 옛 경로가 실제로 지워졌는지, 다른 호출자가 남아 있지 않은지 검색으로 확인한다.
- "함께 고친 호출 지점"이 전부인지, 바뀐 인터페이스의 다른 호출자가 없는지 확인한다.
- 보고에 없는 변경(파일, 설정, 시험)이 있는지 확인한다. 보고되지 않은 변경은 그 자체로 지적 대상이다.

### 4.2 요구와 설계 적합성

- 구현이 설계대로인가.
- **설계가 요구사항과 수락 기준을 실제로 충족하는가.** 설계를 한 모델이 검증할 때 특히 생략하기 쉬운 항목이다.
- "설계와 달라진 점"이 승인된 것인지, 승인 근거가 기록에 있는지 확인한다.
- 설계 자체의 결함은 구현 지적이 아니라 기획설계로 넘긴다(6절).

### 4.3 구조

- 요청한 연결이 입력부터 최종 소비자까지 실제로 이어지는가.
- 각 책임의 소유 모듈이 하나로 분명한가. 같은 입력에 대한 권위 있는 경로나 자료 정의가 둘 이상 생기지 않았는가.
- 20-implementation 6절의 덧대기 형태가 쓰였으면, 보고된 이유가 그 표의 "쓸 수 있는 경우"에 실제로 해당하는지 판정한다.
- 불필요한 간접화, 사용처 없는 필드·옵션·추상화, 제거 조건 없는 임시 코드가 없는가.
- 이전 세션에서 덧댄 코드를 원래 설계로 승계하지 않았는가. 디스크에 있다는 것은 정당성의 근거가 아니다.

### 4.4 계약과 실패 동작

- 입출력 계약과 유지해야 할 기존 계약이 보존됐는가.
- 실패가 원인을 구별할 수 있는 형태로 드러나는가. 조용한 대체, 오류 삼키기, 넓은 예외 처리가 없는가.
- Retry·Timeout·Fallback이 있으면 대상 오류, 한계, 멱등성, 최종 실패 처리가 정해져 있는가.
- 방어 코드가 실제 신뢰 경계에 있는가, 이미 보장된 상태를 반복 검사하는가.

### 4.5 시험

- **수락 시험이 바뀌지 않았는가.** 기대값, 허용 오차, 입력, skip·xfail 표시를 이전 상태와 직접 비교한다. 승인 없이 바뀌었으면 차단 지적이다.
- 추가된 시험의 기대값이 구현과 독립적인가. 구현이나 제품 상수에서 복사한 기대값은 지적한다.
- 시험 대역이 검사할 경로를 우회하거나 결함을 대신 처리하지 않는가.
- 중요 시험의 mutation check 결과가 있는가. 의심스러우면 검증자가 임시 작업 공간(별도 worktree)에서 한 번 직접 해 보고 그 공간은 버린다. 검토 대상 코드에는 손대지 않는다.
- 빠진 고장 경계가 있는가, 같은 경계를 중복 검사하는 시험이 있는가.

### 4.6 의미 변경과 수치

- 동작 보존 리팩토링이라고 보고했는데 결과가 바뀌는 곳이 없는가.
- 의미 변경이면 변경 전후 비교 증거가 보존됐는가.
- 수학 코드는 수식, 좌표계·단위, 수치 오차, 경계 조건, 실패 동작을 대조한다. 허용 오차에 근거가 있는가.
- 계산 결과 재현에 필요한 조건(입력 식별자, 계산 조건, 난수 조건, 환경)이 남아 있는가.

### 4.7 증거 수준 확인

- 구현자가 주장한 증거 수준(공통 5절)을 검증자가 직접 확인한다. 최소한 수락 시험은 검증자가 직접 실행한다.
- 대역 통합 성공을 실제 실행이나 실물 증거로 보고하지 않았는지 확인한다.
- 설계가 요구한 증거 수준에 도달했는지 판정한다.

## 5. 정적 분석과 추가 리뷰

### 5.1 정적 분석 처분 검토

구현자가 최종 변경 상태에 정적 분석(`project-settings.md`(프로젝트 AGENTS.md의 "프로젝트 설정" 절이 있으면 해당 절)에 지정)을 돌리고 처분한 기록을 검토한다.

- 실행 대상이 검토 대상 코드 상태와 같은지 확인한다. 다르면 검증자가 다시 실행한다.
- "오탐", "의도된 계약"으로 처분한 지적은 근거가 실제 코드와 맞는지 하나씩 본다.
- 지적 억제, 규칙 비활성화, 기준 하향으로 등급이 올라가지 않았는지 확인한다.
- 자동 등급만으로 수락하지 않는다.

### 5.2 추가 전문·AI 리뷰

핵심 알고리즘, 복잡한 설계 변경, 검증자 혼자 판단하기 어려운 수치 문제, 설계자가 검증한 고위험 작업(2절)은 다른 모델이나 전문 검토자의 리뷰를 추가로 받는다.

- 추가 리뷰어는 현재 코드와 변경 내용을 실제로 볼 수 있어야 한다. 요약만 보여 주고 받은 의견은 리뷰가 아니다.
- 추가 리뷰의 지적도 6절의 지적과 같이 처분한다.
- 어느 모델의 긍정적 평가도 정확성이나 완료의 증거가 아니다. 판정은 코드·실행·측정 결과로 한다.

## 6. 지적 작성과 처분

### 6.1 지적 작성

지적마다 다음을 적는다. 근거 없는 지적, 취향·스타일만의 지적은 차단으로 올리지 않는다.

```markdown
- 번호: <V-1>
- 위치: <파일·함수·줄>
- 위반 기준: <규칙 문서 절 번호 또는 수락 기준 ID>
- 근거: <관측한 사실, 재현 방법>
- 등급: 차단 / 비차단 / 기술 부채
- 보낼 곳: 구현 / 기획설계
```

| 등급      | 뜻                                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------------ |
| 차단      | 해결 전에는 완료로 판정할 수 없다. 요구 미충족, 계약 위반, 수락 시험 무단 변경, 병렬 구현, 미보고 변경, 고위험 증거 부족 |
| 비차단    | 이번 변경에서 고쳐야 하지만 판정을 막지는 않는다                                                                         |
| 기술 부채 | 이번 변경과 무관한 기존 문제. 기록만 한다                                                                                |

설계 결함은 "보낼 곳: 기획설계"로 적는다. 검증자가 같은 모델로 설계를 했어도 자기 설계를 옹호하지 말고 같은 기준으로 적는다.

### 6.2 처분

구현자(또는 기획설계)는 각 지적을 둘 중 하나로 처분한다.

- **수정**: 고친 위치와 다시 실행한 검증을 적는다
- **근거 있는 기각**: 계약, 실제 실행 경로, 검증 결과에 근거해 지적이 맞지 않음을 설명한다

검증자는 각 처분을 수락하거나 반려한다. 반려하면 이유를 적는다. 같은 지적이 두 번 반려되면 총괄(없으면 사용자)에게 올린다.

### 6.3 재검토 범위

수정 뒤에는 바뀐 부분과, 그 변경이 영향을 주는 호출자·시험·계약을 다시 본다. 영향 범위 밖의 이전 검토 결과는 코드·입력·계약이 그대로이면 재사용한다.

### 7.1 판정 기준

| 판정      | 조건                                                                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 완료      | 요구와 수락 기준 충족, 유지할 계약 보존, 책임과 실행 경로가 분명, 대체된 코드 정리, 요구한 증거 수준 도달, 미해결 차단 지적 없음, 2절 독립성 조건 충족 |
| 부분 완료 | 일부 요구는 충족했으나 차단 지적이나 미검증 범위가 남음. 남은 조건을 명시한다                                                                          |
| 미완료    | 핵심 요구 미충족, 또는 검토를 진행할 수 없는 상태                                                                                                      |

다음은 완료로 판정하지 않는다.

- 시험은 모두 통과했지만 요청한 연결이 끝까지 동작하는지 확인하지 못했다
- 고위험 변경에서 필요한 증거 수준에 도달하지 못했다
- 고위험 변경을 2절 조건 없이 검증했다
- 미해결 차단 지적이 있다

부분 완료·미완료면 원인을 10-planning 7절의 다섯 가지(요구 변경 / 설계 오류 / 구현 오류 / 시험 오류 / 환경·외부 요인) 중 하나로 근거와 함께 분류해 판정 보고에 적는다. 불명확하면 미확정으로 둔다.

### 7.2 판정 보고 (`verdict.md`)

```markdown
## 검증 판정: <작업 ID / 이름>

1. 판정: 완료 / 부분 완료 / 미완료
2. 검증 조건: 교차 모델 / 단일 모델 / 자체 점검, 같은 대화 검토 여부, 검토한 코드 상태(커밋·worktree)
3. 설계 적합성(4.2): 설계가 요구·AC를 충족하는가에 대한 판정과 근거
4. 직접 확인한 것: 실행한 시험·계산, 확인한 증거 수준(공통 5절 번호)
5. 지적 목록과 처분 상태: 차단·비차단·기술 부채별
6. 기획설계로 넘긴 것
7. 미검증 범위와 남은 위험
8. 미완료 원인 분류(부분 완료·미완료일 때)와 완료까지 남은 조건
9. 현재 명세 반영 요청(완료일 때): 반영할 REQ·AC·계약
```

판정 보고는 다음 작업의 인계 문서가 된다. 판정 근거가 없는 항목을 채우려고 문장을 늘리지 않는다.

### 7.3 완료 뒤

완료로 판정하면 기획설계에 현재 명세 반영을 요청한다(10-planning 2.1). 반영이 끝나야 작업이 닫힌다. 완료 판정은 푸시 승인이 아니다. 푸시는 사용자의 명시 승인으로만 한다(40-paseo-role-workflow 4절).
