# 에이전트 규칙 진입점

진행 방식이 정해지지 않았으면 요청 종류와 관계없이 첫 응답 전에 진행 방식을 묻는다. 질문·설명·읽기 전용 조사는 답변에 필요한 규칙·자료만 읽고 답한다. 구현 담당 선택을 강제하지 않으며, 상태를 임의로 확정하지 않는다. 실제 변경 요청(설명 후 수정 요청 포함)은 기존 선택 절차를 따른다. “어떻게 고쳐?”만으로 구현 승인이 되지 않는다.

## 1. 단계별 읽기

실제 변경 시작에는 이 파일, `00-common.md` 핵심(1·3·4·5·8절), 프로젝트 `AGENTS.md`·`CLAUDE.md`(있으면), 현재 작업 기록을 읽는다. 공통 용어·문서 지도·규제 등 나머지 상세는 관련 판단 때 참조한다.

| 현재 단계 | 추가로 읽을 상세 |
| --- | --- |
| 기획·설계 | `10-planning.md` |
| 구현·자체 시험 | `20-implementation.md` |
| 최종 검토 | `30-verification.md`와 관련 구현 기준 |
| 역할 분리 인계·상태 처리 | `40-paseo-role-workflow.md` 관련 절 |
| 계약4 일반개발 | 공통 3.4절과 현재 단계 상세만. 세 역할 문서 전체 일괄 독해 없음 |
| 압축 복구·모델 교대 | 공통 8절: 핵심 제약·현재 인계·마지막 상태·실제 변경본 확인. 무변경 상세 전체 재독 없음 |

역할·계약·규칙이 바뀌거나 기록이 누락·충돌하면 해당 상세를 다시 읽는다. 프로젝트 설정이 필요하면 `project-settings.md`를 참조한다.

## 2. 상시 규칙 (요약 — 원본은 각 문서)

1. **역할 경계:** 기획설계는 제품 코드를 고치지 않고, 구현은 수락 기준·수락 시험을 고치지 않으며, 검증은 코드를 고치지 않는다. 역할 분리 작업의 최종 완료 판정은 검증 역할만 한다. 계약4 일반개발은 공통 3.4의 자체 점검을 따른다.
2. **사실 구분:** `[확인] [제안] [가정] [미확정]`, 하지 않은 것은 `[미실행]`. 근거 없는 수치·현황·검증 결과를 만들지 않는다.
3. **SSOT:** 정보마다 공식 원본은 하나다(`00-common.md` 6절). 같은 규칙을 다른 파일에 복사하지 않는다.
4. **위험도·증거 수준:** `00-common.md` 4절·5절이 유일한 기준이다.
5. **덧대기 금지:** 원래 책임 자리에서 고친다. 대체한 경로는 같은 변경에서 지운다.
6. **역할 분리 인계는 문서로:** `handoff.md` → `impl-report.md` → `verdict.md`. 대화 요약이나 기억으로 인계하지 않는다.
7. **멈춤:** 설계와 코드가 맞지 않거나, 승인 없는 계약·범위·안전 변경이 필요하거나, 규칙끼리 충돌하면 멈추고 근거와 선택지를 보고한다.
8. **완료 ≠ 푸시:** 푸시는 사용자가 화면에서 승인하면 플러그인이 실행한다. 에이전트는 git push를 직접 실행하지 않는다.

작은 작업의 문서 축소는 공통 6.4절을 따른다. 승인·검증 증거·고위험 독립 검토·완료 게이트·명시적 푸시 승인은 유지한다.
