## 1. 판단 우선순위

규칙이 충돌하면 위의 것이 이긴다. 상위 조건을 해치면서 하위 조건을 개선하지 않는다.

1. 안전, 보안, 데이터 무결성, 법적·규제 요구, 반드시 보존할 외부 계약
2. 기획설계가 확정하고 승인된 요구사항과 수락 기준
3. 기존의 검증된 동작과 실험·수학적 의미
4. 책임의 명확성, 구조의 일관성, 변경 범위
5. 단순성, 성능, 개발·검증 비용

이 순서로도 판단이 서지 않으면 멈추고 보고한다.

## 2. 사실 표기와 용어

### 2.1 사실 표기

주요 진술에 아래 중 하나를 붙인다.

| 표기       | 의미                                     | 함께 적을 것                        |
| ---------- | ---------------------------------------- | ----------------------------------- |
| `[확인]`   | 파일·실행 로그·시험·승인 기록으로 확인함 | 경로·위치·커밋, 환경·일시 또는 링크 |
| `[제안]`   | 채택을 요청하는 구조·선택                | 대안, 이유, 영향, 승인 상태         |
| `[가정]`   | 합리적이지만 확인하지 못함               | 틀렸을 때의 위험과 확인 방법        |
| `[미확정]` | 사용자 결정이나 추가 증거가 필요함       | 영향받는 작업과 착수 차단 여부      |

하지 않은 실행은 `[미실행]`, 확인하지 못한 정보는 `[미확인]`으로 적는다. 승인된 명세는 목표의 기준이고, 코드·스키마·설정·실행 결과는 해당 커밋과 환경에서 관측된 동작의 근거다. 둘이 다르면 GAP으로 기록하며 어느 쪽도 자동으로 채택하지 않는다.

### 2.2 용어

- **REQ / NFR:** 기능 요구 / 비기능 요구. 프로젝트 전체에서 유일한 ID(`REQ-0001`).
- **AC(수락 기준):** 요구 충족을 외부에서 관측할 수 있는 조건. `REQ-0001.AC-01`.
- **수락 시험(TEST):** AC를 검증하는 시험 또는 수동 확인 절차. AC ID에 일련번호를 붙인다.
- **ID 발급:** 발급 방식은 `project-settings.md`(프로젝트 AGENTS.md의 "프로젝트 설정" 절이 있으면 해당 절)에서 한 번만 정한다. 여러 에이전트가 동시에 발급할 수 있으면 작업 ID 접두어나 단일 예약 절차로 충돌을 막는다. 쓰지 않게 된 번호는 재사용하지 않는다.
- **목표(Target):** 승인된, 앞으로 구현할 의도와 수락 기준.
- **현재 적용 기준(Baseline):** 특정 릴리스·환경에 실제로 적용된 계약과 동작. 승인만 된 것은 Baseline이 아니다.
- **변경 기록(Change record):** 무엇을 왜 바꿨는지의 증거(`docs/changes/`). 완료 뒤에도 보존하되 현행 계약을 재정의하지 않는다.
- **GAP:** 승인된 목표와 확인한 현재 동작의 차이.
- **계약:** API, 자료 형식·스키마, 설정 키, 출력의 의미, 오류·권한·외부 연동 약속.
- **유지 / 통합 / 교체 / 제거:** 영향받는 기존 구현의 판정. 교체는 새 경로로 전환하면서 구 경로를 철거하는 것이다.
- **동작 보존 리팩토링 / 의미 변경:** 외부 관측 동작을 보존하는 구조 변경 / 결과나 의미가 바뀌는 변경.
- **덧대기:** 원래 책임 자리를 고치지 않고 옆이나 위에 같은 일을 하는 경로를 추가하는 것(20-implementation 6절이 판정 기준).
- **증거:** 코드 위치, 시험·실행 로그, 스키마, 승인 이력처럼 다시 확인할 수 있는 자료.
- **기준 커밋(base_commit):** 설계가 근거로 삼은 저장소 상태.
- **기획설계 인계서 / 구현 인계 보고 / 검증 판정 보고:** 역할 사이에 넘기는 문서. 형식은 각각 10-planning 8절, 20-implementation 8절, 30-verification 7.2절.

## 3. 운영 모드

Paseo role-workflow는 대화를 시작할 때 **연합개발 / 일반개발**을 묻는다(기본값 연합개발). 규칙의 운영 모드는 이렇게 대응한다. 상태 블록·안전장치와의 대응은 `40-paseo-role-workflow.md`.

| 운영 모드 | role-workflow 구성                                                                                                                    | 쓰는 때                                   |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 교차 모델 | 연합개발. plan 대화(기본 Claude) = 기획설계 + 검증, execute 대화(기본 Codex) = 구현                                                   | 기본값                                    |
| 단일 모델 | 연합개발이지만 plan과 execute를 같은 모델이 맡는다(예: Claude가 실행 담당)                                                            | 다른 모델을 쓸 수 없을 때                 |
| 일반 개발 | 일반개발. 최초 대화가 기획설계·검증, 이후 선택한 별도 대화가 구현을 맡고 자동 인계한다(3.4) | 경미 작업, 또는 사용자가 지정한 일반 작업 |

### 3.1 모든 모드 공통

- 역할 경계는 모드와 상관없이 지킨다. 한 에이전트가 여러 역할을 맡아도 지금 어느 역할로 일하는지 밝히고 그 역할 문서를 따른다.
- 역할 사이의 인계는 저장소 문서로 한다. 대화 요약이나 기억으로 인계하지 않는다.
- 같은 모델의 자체 점검은 독립 검토가 아니다.
- 고위험 작업은 구현에 참여하지 않은 다른 모델이 검증하기 전까지 최대 "부분 완료"다.

### 3.2 교차 모델 (연합개발)

- plan 대화는 10-planning과 30-verification을, execute 대화는 20-implementation을 따른다.
- 인계는 상태 블록의 `next`·보고 본문에 인계 문서의 경로와 요약을 담아 한다(40-paseo-role-workflow 2절). 받는 쪽은 그 파일과 해당 역할 문서를 읽고 시작한다.
- plan 대화가 자기 설계를 검토하게 되므로 30-verification 2절의 교차 모델 조건(다시 읽기, 설계 적합성 별도 판정, 고위험 추가 검토)을 지킨다.
- 구현에 참여한 대화는 같은 작업의 검증자가 될 수 없다.
- 같은 책임·계약·스키마를 두 대화가 동시에 바꾸지 않는다(10-planning 7절 동시 수정). role-workflow가 같은 폴더 동시 수정을 경고하면 멈추고 보고한다.

### 3.3 단일 모델

- 역할마다 새 세션을 쓴다. 검증 세션은 구현 세션의 추론·대화를 보지 않고 설계, 인계 보고, 코드만 본다.
- 기획설계의 게이트(10-planning 4절)를 통과하고 인계서를 파일로 남긴 뒤에만 구현으로 넘어간다.
- 독립 검토가 필요한 단계(수락 시험 사전 검토, 고위험 검증)는 다른 모델 또는 사용자가 한다. 사용자가 검토할 때는 대상(AC ↔ 수락 시험 대응표 등)을 한 화면 분량으로 요약해 넘긴다.
- 판정 보고에 "단일 모델 검증"을 적는다.

### 3.4 일반 개발

- **역할 고정:** 최초 실행한 대화의 모델·추론은 기획·설계·검증을 맡는다. 이후 선택은 구현 담당 에이전트(Claude Code / Codex), 모델, 추론 강도에만 적용한다. 최초 대화를 구현 대화로 교체하지 않는다.
- **자동 인계:** 최초 대화가 기획설계 인계서(`handoff.md`)를 작성하고 `plan`으로 별도 구현 대화에 넘긴다. 구현 담당은 구현·자체 시험 후 `impl-report.md`와 `result`를 반환한다. 최초 대화가 실제 코드와 시험을 확인하고 `verdict.md`로 판정한다. 미완료면 `plan`으로 보완을 지시한다. 정확한 상태·호스트 계약은 40-paseo-role-workflow를 따른다.
- **선택:** 구현 담당을 고른 뒤 다시 묻지 않는다. `askExecutorModel`이 꺼져 있으면 저장된 구현 담당을 쓰며, 없으면 사용자에게 선택을 요청한다. 질문 대기·미응답·생성 실패 때 최초 모델이 구현까지 대신하지 않는다.
- **같은 제공자·모델:** 같은 제공자의 다른 모델도 구현 담당으로 선택할 수 있다. 같은 모델이어도 별도 구현 대화를 쓰고, 판정 조건은 단일 모델로 보고한다. 별도 대화만으로 독립 검토를 충족했다고 보지 않는다.
- 위험도를 먼저 정하고 공통 4절 및 10-planning 3.3에 따라 범위·AC·설계·인계를 준비한다. 고위험의 추가 독립 검토 조건은 30-verification 2절을 따르며, 조건을 충족하기 전에는 완료로 판정하지 않는다.
- 최종 검증은 구현 담당이 하지 않는다. 최초 대화의 판정이 없거나 불합격이면 전체 작업은 완료되지 않는다. 완료 판정과 푸시 승인은 별개다.
- **이전 세션:** 계약 3부터 이 구조를 적용한다. 계약 1의 기존 일반개발은 단일 담당 동작을 유지하며 읽기만으로 역할을 재배정하지 않는다. 이미 구현에 참여한 대화를 같은 작업의 독립 검증자로 복구하지 않는다. 전환은 현재 변경·대화 상태·인계 문서를 확인한 별도 작업으로 한다.

## 4. 위험도 — 유일한 기준

| 위험도 | 기준 예시                                                                                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 경미   | 계약·실행 동작·영구 데이터·보안에 영향 없는 표현·문서·국소 정리                                                                                                    |
| 일반   | 기능 추가, 버그 수정, 인터페이스·입출력 처리 변경, 여러 모듈 수정, 되돌릴 수 있는 계약 변경                                                                        |
| 고위험 | 핵심 수학 알고리즘, 계산 의미, 실물 장치 제어, 안전 동작, 의료·규제 판단, 데이터 무결성, 보안·인증·권한, 개인정보, 동시성, 저장 구조 변경, 데이터 삭제·비가역 이관 |

- 코드량이 아니라 실패의 영향과 복구 난이도로 정한다. 목록에 없어도 실패 영향이 같으면 같은 등급이다.
- 애매하면 높은 쪽으로 정하고 근거를 적는다.
- 기획설계가 정해 인계서에 적는다. 받지 못한 구현자는 이 표로 판단해 인계 보고에 적는다.
- 진행 중 영향이 드러나면 재분류하고 건너뛴 단계를 수행한다.
- 승인된 조직 위험 정책이 있으면 `project-settings.md`(프로젝트 AGENTS.md의 "프로젝트 설정" 절이 있으면 해당 절)에 위치를 적고 그것을 따른다.

역할별로 위험도에 따라 할 일: 기획설계 단계 적용은 10-planning 3.3, 구현자 자체 검증은 20-implementation 7.1, 검증 독립성은 30-verification 2절.

## 5. 증거 수준 — 유일한 기준

다음은 서로 다른 상태이며 섞어 보고하지 않는다.

1. 소스·import·빌드 성공
2. 대역 통합 성공(Mock·Stub·Fake 사용)
3. 실제 계산 엔진·실제 실행 환경에서의 실행과 결과 확인
4. 사용 가능한 실물 증거(실제 장치·시스템의 관측된 동작)
5. 실물 준비 완료(환경·연결은 준비됐으나 실행 증거는 아님)

- 기획설계는 작업마다 필요한 수준을 번호로 지정한다.
- 구현자는 필요한 수준과 실제 도달한 수준을 함께 보고한다.
- 검증자는 도달 수준을 직접 확인한다.
- 대역 통합(2)을 실제 실행(3)이나 실물 증거(4)로 보고하지 않는다.

| 전역 구조·의존 방향                     | `docs/ARCHITECTURE.md`                                                          | 여러 작업이 공유하는 구조만. 필요할 때 만든다 |
| API·자료·설정 계약                      | OpenAPI, 스키마·마이그레이션, 설정 스키마                                       | 기계가 읽는 계약 우선. 설명 문서는 참조       |
| 작업별 목표·설계(Target, Change record) | `docs/changes/<작업ID>/spec.md`, `design.md`                                    | 해당 변경의 제안과 근거                       |
| 작업 분해·상태                          | `docs/changes/<작업ID>/tasks.md`                                                | 의존·진행·검증 링크. 요구를 재정의하지 않는다 |
| 기획설계 인계서                         | `docs/changes/<작업ID>/handoff.md`                                              | 10-planning 8절                               |
| 구현 인계 보고                          | `docs/changes/<작업ID>/impl-report.md`                                          | 20-implementation 8절                         |
| 검증 판정 보고·지적                     | `docs/changes/<작업ID>/verdict.md`                                              | 30-verification 6–7절                         |
| 결정 기록                               | `docs/decisions/ADR-NNNN-<주제>.md`                                             | 대체된 결정은 지우지 않고 연결                |
| 수락 시험                               | `tests/acceptance/`                                                             | 시험 명세·코드·실행 결과·검토 상태를 구분     |

경로는 기본값이다. 기존 저장소에 같은 목적의 문서가 있으면 그것을 쓰고, 실제 경로는 `project-settings.md`(프로젝트 AGENTS.md의 "프로젝트 설정" 절이 있으면 해당 절)에서 한 번만 정한다.

### 6.2 SSOT 규칙

- 한 사실은 한 곳에만 쓴다. 다른 문서에서는 다시 쓰지 않고 링크한다.
- 정보끼리 한 줄 서열을 매기지 않는다. 요구사항은 승인된 spec, API는 계약 파일, 자료 구조는 적용된 스키마처럼 정보별 원본에서 확인한다.
- 문서는 현재 상태를 적는다. 바뀐 이력은 버전 관리와 결정 기록에 둔다.
- 캐시·조회용 복제·이관 중 임시 이중 경로는 권위 있는 쓰기 주체, 동기화 규칙, 중복 부작용 방지, 종료 조건을 갖출 때만 허용한다.

### 6.3 역할별 쓰기 범위

| 역할     | 쓸 수 있는 곳                                                                                                                                          | 쓰지 않는 곳                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------- |
| 기획설계 | `docs/`(spec·design·tasks·handoff·ADR·현재 명세), `tests/acceptance/`(project-settings.md 또는 프로젝트 AGENTS.md의 프로젝트 설정 절에 허가가 있을 때) | 제품 코드, DB 스키마, 운영 설정, 실데이터 |
| 구현     | 제품 코드, 구현 범위 시험, 바꾼 인터페이스와 함께 고칠 설정·문서, `impl-report.md`, tasks 상태 칸                                                      | 수락 기준·수락 시험, spec·design 본문     |
| 검증     | `verdict.md`, tasks 상태 칸                                                                                                                            | 제품 코드, 시험, 설계 문서                |

## 7. 작업 흐름

```text
[사용자 요청]
     │
기획설계 ── STEP 0–6 (10-planning 4절)
     │      └ 일반·고위험: 수락 시험 사전 검토 요청 → 검증(30-verification 3절)
     │
     ├─ 게이트 G1–G4 통과 → handoff.md
     ▼
구현 ── 착수 전 확인(20-implementation 2절) → 구현·자체 검증 → impl-report.md
     │      └ 멈춤 보고 → 기획설계(10-planning 7절) → 재인계
     ▼
검증 ── 검토(30-verification 4–6절) → verdict.md
     ├─ 미완료·부분 완료 → 원인 분류 → 해당 역할로 되돌림(10-planning 7절)
     └─ 완료 → 기획설계가 현재 명세(Baseline)에 반영 → tasks에서 작업 닫기
```

작업은 현재 명세 반영까지 끝나야 닫힌다.

## 8. 세션·문맥 압축·모델 교대

- 작업 시작, 문맥 압축 복구, 세션·모델 교대 뒤에는 편집이나 검토를 재개하기 전에 `README.md`, 프로젝트의 `AGENTS.md`·`CLAUDE.md`(있으면), 이 문서, 맡은 역할 문서, 해당 작업 문서(spec·design·tasks·인계 문서)를 실제로 다시 읽는다. 압축 요약이나 "이전에 읽었다"는 기록으로 대신하지 않는다.
- 이전 대화 요약이나 모델의 기억으로 승인·설계·검증 상태를 복원하지 않는다.
- 재독은 기존 검증을 모두 다시 돌리라는 뜻이 아니다. 검증 결과는 대상 코드·입력·환경·계약이 그대로일 때만 재사용한다.
- 세션을 끝내기 전에 결정, 미해결 사항, 검증 상태, 다음 작업을 저장소 문서에 반영한다.
- 읽지 못했거나 접근이 막힌 문서·코드는 `[미확인]`으로 적고, 그 정보가 전제인 작업은 보류한다.

## 9. 규제 프로젝트에만 추가 적용

의료기기 소프트웨어, 허가사항, 의료적 성능·사용 목적, 환자 자료·안전에 영향이 있는 것으로 **확인된 작업에만** 적용한다. 적용 법령·표준·허가 범위는 관련 책임자가 확인하며, 에이전트가 의무 적용을 임의로 정하지 않는다.

- 조직의 ISO 13485 기반 품질문서·설계변경 절차가 있으면 그 설계 입력·출력·검증·승인·추적성 규칙을 먼저 확인한다.
- 필요에 따라 ISO 14971 위험관리, IEC 62304 소프트웨어 생명주기, 식약처 디지털의료기기 법령·품질관리기준의 적용 범위와 버전을 담당자가 검토한다.
- 자료셋·모델 버전·전처리·성능 주장의 변경이 임상적 의미, 잔여위험, 허가 범위, 제출자료, 사용설명서에 미치는 영향을 표시한다. 임상 성능이나 규제 해석을 임의로 확정하지 않는다.
- 규제 영향이 있는 작업은 고위험(4절)이며 경미 경로·일반 개발 모드를 쓰지 않는다.

## 10. 보고

- 단계 보고 순서: 한 줄 요약 → 자세한 요약 → 위험·미확정 → 사용자 승인이 필요한 것 → 근거·출처 → 다음 작업과 인계 가능 여부.
- 2.1의 표기를 붙인다. 하지 않은 시험·확인·승인을 완료로 적지 않는다.
- 어느 모델의 동의나 긍정적 평가도 정확성이나 완료의 증거가 아니다. 판단은 코드·계산·측정 결과로 한다.
- 내용 없는 항목을 채우려고 문장을 늘리지 않는다. 해당 없으면 "없음"이라고 적는다.
